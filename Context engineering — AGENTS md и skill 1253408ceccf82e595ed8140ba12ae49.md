# Context engineering — AGENTS.md и skill

**Обязательная, ★★**

## Зачем это

Сделать так, чтобы coding-агент вёл себя как нормальный middle+ разработчик именно вашего проекта: соблюдал конвенции, слои архитектуры, паттерны обработки ошибок — а не писал generic-код, который формально работает, но ломает архитектуру.

## Краткая теория

- [**AGENTS.md**](https://agents.md/) — открытый формат project instructions, который поддерживают разные coding agents (не завязан на конкретный продукт вроде Cursor Rules).
- **Agent Skills** — открытый формат reusable инструкций под конкретный тип задачи (например, `implement-api-endpoint/SKILL.md`).
- **Context budget → progressive disclosure** — не пытайтесь впихнуть все правила в один файл; выносите специфичные инструкции в отдельные skills, которые подгружаются только когда нужны.
- **Instructions hierarchy** — глобальные правила проекта ([AGENTS.md](https://agents.md/)) vs локальные для конкретной задачи (skill).
- **Negative instructions** — не только "что делать", но и "чего не делать" (например, "не используйте console.log").
- **Executable checks** — инструкция ценна настолько, насколько её можно проверить автоматически, а не только "на глаз".

Главное отличие хорошей инструкции от карго-культа:

```
❌ Always write good tests. Follow best practices.

✅ When adding an API endpoint:
1. Add the route to src/api/routes.
2. Put business logic in src/domain.
3. Validate request input using ...
4. Add integration tests under tests/api.
5. Run npm test и npm run lint.
```

## Шаг 0. Выберите кодовую базу

Два варианта:

**А. Свой репозиторий с прошлого курса или проекта (рекомендуется)** — учебный проект, курсовая, пет-проект. Работаете с реальными, а не искусственно заложенными конвенциями. Раз репозиторий ваш и не публиковался широко, агент точно не мог «подсмотреть» его конвенции из обучающих данных.

**Б. Открытый проект**, если своего подходящего под рукой нет. Где искать: `gothinkster/realworld` (эталонные реализации одного приложения на десятках стеков, архитектура — часть замысла), репозитории по темам `clean-architecture`/`hexagonal-architecture`/`ddd-example`, официальные starter-киты фреймворков (например, NestJS examples).

**Чек-лист самопроверки** (пройдите сами — если хотя бы 2-3 пункта не выполняются, возьмите другой репозиторий):

- [ ]  Есть выраженное разделение слоёв (controllers/handlers ≠ business logic ≠ data access) — не один файл на 200 строк
- [ ]  Разумный размер: 1000–10000 строк — не тривиальный и не безразмерный
- [ ]  Есть тесты, которые реально гоняются (`npm test`/`pytest` возвращает pass/fail)
- [ ]  Есть хотя бы 5-7 неочевидных, но обнаружимых конвенций (свой error-handling паттерн, naming convention, helper-обёртки и т.п.) — если с ходу не можете назвать столько, репозиторий слишком простой
- [ ]  Популярный стек, с которым агент нормально работает

<aside>
⚠️

**Только для варианта Б:** если репозиторий популярный и легко гуглится, агент может уже «знать» его конвенции из обучающих данных или веб-поиска. На время baseline-прогона отключите агенту веб-доступ.

</aside>

## Шаг 1. Baseline — без правил

Попросите агента выполнить небольшую задачу, которая затрагивает несколько слоёв архитектуры (api/domain/repository/ui), а не один файл. Можно взять один из готовых примеров ниже, или свою фичу примерно того же уровня сложности (час-два работы без агента, несколько слоёв) — главное, чтобы она естественно подходила под ваш проект. Примеры, подходящие почти к любому проекту:

- **Мягкое удаление (soft delete)** сущности — вместо реального удаления запись помечается как удалённая (`deleted_at`/`is_deleted`), исключается из обычных списков, но остаётся в базе; нужен эндпоинт восстановления.
- **Экспорт данных пользователя** («скачать мои данные») — эндпоинт/кнопка собирает данные пользователя из нескольких таблиц/сервисов в один файл (JSON/CSV), с проверкой прав доступа (только свои данные).
- **Смена пароля/email в личном кабинете** — форма с валидацией (текущий пароль верен, новый email не занят), хешированием, инвалидацией старых сессий, возможно — письмом-подтверждением.
- **(запасной вариант) Пагинация + фильтрация списка** — добавить в существующий список `?page=&limit=&status=`: затрагивает API-слой (парсинг query), domain (что считается валидным фильтром) и repository (эффективный запрос с limit/offset).

Задача должна быть небольшой (час-два работы) и давать агенту простор случайно нарушить именно те конвенции, которые вы потом будете проверять check-скриптом.

**Что такое «прогон» и зачем их несколько.** Один прогон — это одна попытка агента решить задачу «с нуля»: вы берёте чистое состояние кода (новая ветка/копия репозитория), открываете новый чат/сессию с агентом (чтобы он не помнил предыдущий запуск) и даёте точно такой же промпт. 

<aside>
☝🏻

Агент — недетерминированный: на один и тот же промпт он может в один раз написать код с тремя нарушениями конвенций, а в другой раз — случайно вести себя аккуратнее. Один прогон может обмануть — поэтому нужно несколько независимых попыток, чтобы видеть типичное поведение, а не случайность.

</aside>

### Как это делать на практике:

1. Зафиксируйте чистое состояние кода (коммит/тег) до начала.
2. Создайте отдельную ветку (например, `baseline-attempt-1`), дайте агенту задачу, сохраните результат (коммит).
3. Вернитесь к чистому состоянию, повторите в `baseline-attempt-2`, затем в `baseline-attempt-3` (если делаете три).
4. Запустите check-скрипт (его вы пишете **позже в шаге 4**) на каждой ветке отдельно — он считает, сколько конкретных нарушений в каждом прогоне (например: «прогон 1 — 3 нарушения, прогон 2 — 1, прогон 3 — 2»). Эти числа и есть ваш baseline, с которым вы потом сравните результат после добавления [AGENTS.md/skill](http://AGENTS.md/skill).

## Шаг 2. Сформулируйте конвенции

Если брали чужой/найденный репозиторий — это reverse engineering: изучите код, сформулируйте 5–7 реально соблюдаемых, но неочевидных правил.

## Шаг 3. Напишите AGENTS.md и один reusable skill

```
skills/
  implement-api-endpoint/
    SKILL.md
```

Инструкции должны быть **проверяемыми** (см. пример в теории), а не общими пожеланиями.

## Шаг 4. Повторите задачу с контекстом

Та же задача, что в шаге 1, но теперь агенту доступны [AGENTS.md](http://AGENTS.md) и skill. Сравните нарушения конвенций до/после — не «на глаз», а через **автоматическую проверку**. Допустимы два варианта:

**Вариант 1 — скрипт или линтер (предпочтительно).** Обычный исполняемый скрипт на любом языке (Node.js/Python/bash), который вы запускаете из терминала как `node check.js` — он читает файлы обычным кодом (grep/regex, можно AST), без участия LLM, и печатает число нарушений. 

Тогда же можно взять готовый линтер (ESLint с кастомным правилом, архитектурный линтер типа `dependency-cruiser` для правил вроде «domain не импортирует api») вместо самописного скрипта, если он покрывает ваши конкретные конвенции.

Пример логики для самописного скрипта:

```
• пройти по всем файлам src/domain/**, найти import ... from '.../api/...' — это запрещённый импорт
• grep по всему проекту на console.log
• в каждом файле в src/api/routes/**, добавленном/изменённом в текущей задаче, проверить наличие вызова validate(...)
• проверить, что для каждого нового файла в src/api/ есть соответствующий файл в tests/api/
• вывести итог: «нарушений: N» + список файлов/строк, где найдено
```

**Вариант 2 — промпт (попросить самого агента/другую LLM-сессию проверить код на соответствие конвенциям).** Быстрее в настройке, но менее надёжно: LLM может пропустить реальное нарушение или, наоборот, показать ложное там, где его нет. 

**Если выбрали этот вариант — обязательно перепроверьте результат глазами** — пройдитесь по коду сами и сверьте, что найденные LLM нарушения реальны, а не пропущено что-то очевидное. В отчёте укажите, что проверка была через promt + ручную сверку.

Конкретные проверки (в любом из двух вариантов) будут зависеть от того, какие конкретно конвенции вы сформулировали в шаге 2. Запустите проверку на сохранённых baseline-ветках из шага 1 и на результате после добавления контекста, чтобы получить числа «до/после».

## Шаг 5. Проверьте генерализуемость

Прогоните тот же [AGENTS.md/skill](http://AGENTS.md/skill) на **втором, структурно похожем, но другом задании** из того же списка примеров, что в шаге 1 (например, если в шаге 1 было soft delete, теперь возьмите экспорт данных или смену пароля). Если правила были написаны под конкретный кейс, а не как общий принцип — это здесь вскроется.

## Что сдаётся

- `AGENTS.md` и skill;
- check-скрипт;
- логи/результаты обоих прогонов (baseline и после настройки контекста), по 2–3 baseline-запуска;
- результат проверки на скрытом втором задании;
- `REPORT.md`: какие ошибки агент совершал изначально, какими правилами устранены, какие инструкции оказались бесполезными, и результат generalization-теста.

## Чек-лист перед сдачей

- [ ]  Кодовая база выбрана, чек-лист из шага 0 пройден самостоятельно
- [ ]  Baseline прогнан 2–3 раза, нарушения зафиксированы
- [ ]  [AGENTS.md](http://AGENTS.md) + skill написаны с проверяемыми инструкциями (не "write good tests")
- [ ]  Есть автоматическая проверка (скрипт/линтер, или промпт + ручная сверка)
- [ ]  Прогон с контекстом сделан, сравнение до/после — по числам check-скрипта
- [ ]  Проведён generalization-тест на втором задании
- [ ]  [REPORT.md](http://REPORT.md) содержит все требуемые пункты

## Критерии оценки

Суммарно за лабу — **20 баллов**.

| Критерий | Баллы | Не зачтено | Частично | Полностью |
| --- | --- | --- | --- | --- |
| **Качество инструкций** | 6 | 0 — общие пожелания ("write good tests") | 3 — смешаны общие и конкретные пункты | 6 — все инструкции проверяемые, конкретные |
| **Измеримость эффекта** | 6 | 0 — только субъективное описание в [REPORT.md](http://REPORT.md) | 3 — есть числа, но один baseline-прогон или проверка через промпт без ручной сверки | 6 — автоматическая проверка (скрипт/линтер, или промпт с подтверждённой ручной сверкой) + 2-3 baseline прогона + числа до/после |
| **Генерализуемость** | 4 | 0 — не проверялась | 2 — проверена, но правила оказались привязаны к кейсу | 4 — правила сработали на скрытом втором задании |
| **Отчёт** | 4 | 0 — формальный, без анализа | 2 — есть анализ, но поверхностный | 4 — чёткий разбор: что сработало, что нет, почему |
